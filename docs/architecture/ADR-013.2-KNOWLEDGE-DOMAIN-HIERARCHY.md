# ADR-013.2 — Knowledge Domain Hierarchy

## Estado

Implementado

## Fecha

2026-07-22

---

# 1. Contexto y Problema

El Knowledge Domain Intelligence Engine introdujo la capacidad de representar conocimiento profesional mediante dominios y competencias.

Las evoluciones anteriores establecieron:

* ADR-013: Knowledge Domain Intelligence Engine.
* ADR-013.1: Domain Scoring Strategy.

Inicialmente, los dominios funcionaban como estructuras independientes con competencias asociadas.

Ejemplo:

```text
Procurement
 |
 +-- Supplier Management
 +-- Purchasing
```

Este modelo permite evaluar conocimiento dentro de un dominio individual, pero no representa relaciones entre dominios profesionales.

En el mundo laboral real, el conocimiento se organiza mediante estructuras jerárquicas.

Ejemplo:

```text
Supply Chain
      |
      +-- Procurement
      |
      +-- Logistics
      |
      +-- Inventory Management
```

El sistema necesita comprender que un dominio puede formar parte de un dominio superior más amplio.

---

# 2. Decisión Arquitectónica

Se introduce el concepto de jerarquía de Knowledge Domains.

Un dominio puede tener una relación opcional con un dominio superior mediante:

```text
Parent Domain
      |
      |
Child Domain
```

Esta relación permite representar estructuras profesionales jerárquicas manteniendo compatibilidad con dominios existentes.

Ejemplo:

```text
Supply Chain
      |
      +-- Procurement
             |
             +-- Supplier Management
             +-- Purchasing
```

---

# 3. Nuevo Modelo Conceptual

La arquitectura evoluciona desde:

```text
Competency
     |
     ↓
Knowledge Domain
```

hacia:

```text
Knowledge Domain Hierarchy

Domain
 |
 +-- Child Domain
        |
        +-- Competencies
```

Los dominios pueden existir como:

* dominios raíz,
* subdominios,
* dominios especializados.

---

# 4. Nuevo Contrato Implementado

El modelo `KnowledgeDomain` fue extendido para soportar jerarquía:

```ts
interface KnowledgeDomain {

  id: string;

  name: string;

  parentDomainId?: string;

  competencies:
    KnowledgeDomainCompetencyWeight[];

}
```

La propiedad:

```ts
parentDomainId?: string;
```

es opcional.

Esto permite:

* dominios raíz sin dependencia superior,
* dominios hijos asociados a un dominio padre,
* compatibilidad con dominios existentes.

---

# 5. Estrategia de Jerarquía

La jerarquía soporta:

## Dominios raíz

Ejemplo:

```text
Supply Chain
```

## Subdominios

Ejemplo:

```text
Supply Chain
      |
      +-- Procurement
```

## Especializaciones futuras

Ejemplo:

```text
Procurement
      |
      +-- Supplier Management
```

---

# 6. Impacto en Scoring

ADR-013.1 define el scoring dentro de un dominio individual.

ADR-013.2 prepara la arquitectura para futuras capacidades de agregación jerárquica.

Ejemplo futuro:

```text
Supply Chain Score

=
Weighted Child Domain Scores
+
Direct Competency Scores
```

La implementación actual mantiene el scoring existente sin alterar el comportamiento de ADR-013.1.

---

# 7. Validaciones Necesarias

La arquitectura futura deberá garantizar:

## Prevención de ciclos

No permitir:

```text
A
 |
 B
 |
 A
```

## Control de profundidad

La jerarquía deberá mantener una profundidad razonable.

Recomendación inicial:

```text
3-4 niveles máximos
```

## Integridad referencial

Un dominio hijo debe apuntar a un dominio existente dentro del catálogo de Knowledge Domains.

# 12. Resultado Final

ADR-013.2 establece la evolución del Knowledge Domain Engine desde un modelo plano hacia una estructura jerárquica de conocimiento profesional.

La implementación inicial proporciona:

```text
Supply Chain
      |
      +-- Procurement
```

y prepara Global Career AI para representar relaciones complejas entre:

* competencias,
* dominios,
* conocimiento profesional,
* trayectorias laborales.

Esta decisión mantiene separación entre:

```text
ProfessionalDomain
        ≠
KnowledgeDomain
```

permitiendo que cada modelo evolucione dentro de su propia responsabilidad arquitectónica.
