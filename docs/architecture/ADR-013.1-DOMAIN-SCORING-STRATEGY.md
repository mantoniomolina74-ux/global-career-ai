# ADR-013.1 — Knowledge Domain Scoring Strategy

## Estado

Aceptado

## Fecha

2026-07-22

---

# 1. Contexto y Problema

El Knowledge Domain Intelligence Engine introdujo la capacidad de representar conocimiento profesional agrupado por dominios funcionales.

La primera versión del modelo permitía asociar competencias a un dominio mediante una lista simple:

```ts
competencyIds: string[]
```

Este enfoque era suficiente para representar pertenencia, pero no permitía expresar la importancia relativa de cada competencia dentro de un dominio.

Ejemplo:

Un dominio como:

```
Supply Chain
```

puede contener:

* Procurement
* Supplier Management
* Inventory Management
* Logistics

Sin embargo, no todas las competencias tienen el mismo impacto para evaluar conocimiento profesional.

El sistema necesitaba evolucionar desde una relación:

```
Domain → Competencies
```

hacia una relación ponderada:

```
Domain → Weighted Competencies
```

---

# 2. Decisión Arquitectónica

Se introduce un modelo de competencias ponderadas dentro de los Knowledge Domains.

Cada dominio ahora define sus competencias mediante pesos relativos:

```ts
KnowledgeDomainCompetencyWeight
```

permitiendo representar:

* importancia de una competencia dentro del dominio,
* influencia en el cálculo del dominio,
* futuras estrategias de aprendizaje y adaptación.

Nuevo contrato conceptual:

```
Knowledge Domain
        |
        |
        +-- Competency A (weight)
        |
        +-- Competency B (weight)
        |
        +-- Competency C (weight)
```

---

# 3. Nuevo Contrato de Datos

Antes:

```ts
interface KnowledgeDomain {
  id: string;
  name: string;
  competencyIds: string[];
}
```

Después:

```ts
interface KnowledgeDomainCompetencyWeight {
  competencyId: string;
  weight: number;
}

interface KnowledgeDomain {
  id: string;
  name: string;
  competencies: KnowledgeDomainCompetencyWeight[];
}
```

---

# 4. Estrategia de Scoring

El Domain Score se calcula considerando:

* evidencia encontrada,
* score individual de competencia,
* peso relativo dentro del dominio.

Fórmula conceptual:

```
Domain Score =
Σ (Competency Score × Competency Weight)
/
Σ (Competency Weight)
```

Donde:

```
Competency Score
```

representa la evidencia disponible para una competencia específica.

Ejemplo:

Dominio:

```
Supply Chain
```

Competencias:

```
Procurement             weight: 0.40
Supplier Management     weight: 0.35
Inventory Management    weight: 0.25
```

Resultado:

```
Domain Score =
(
 Procurement Score × 0.40
+
 Supplier Score × 0.35
+
 Inventory Score × 0.25
)
/
1.0
```

---

# 5. Beneficios de la Decisión

Esta evolución permite:

## Mayor precisión

El sistema diferencia competencias críticas de competencias complementarias.

## Mejor interpretación profesional

Un candidato puede demostrar fortaleza en un dominio aunque no tenga todas las competencias posibles.

## Preparación para aprendizaje adaptativo

El Knowledge Engine podrá identificar:

* fortalezas,
* brechas,
* competencias prioritarias.

## Base para inteligencia de carrera

Los dominios dejan de ser simples agrupaciones y comienzan a representar conocimiento profesional estructurado.

# 7. Impacto en Arquitectura

Componentes afectados:

```
Knowledge Intelligence Engine

        |
        |
        +-- knowledgeTypes.ts
        |
        +-- Domain Scoring Layer
        |
        +-- Competency Scoring Layer
        |
        +-- Future Learning Intelligence
```

El cambio mantiene compatibilidad con la arquitectura Clean Architecture porque:

* los contratos evolucionan explícitamente,
* la lógica de scoring permanece desacoplada,
* los dominios no dependen de implementaciones externas.
